# Правила боя

Как устроен бой в discord-rpg: механика бит, этапы раунда, формулы урона, ИИ противника. Описывает **текущую реализацию** (`backend/src/Battle/*`, `BattleService`, `BattleController`) — этот документ должен использоваться как опора при проектировании "комнаты боя" (визуальной арены/лобби для PvP и не только).

---

## 1. Базовая механика: биты

**Бита** (`Bit`) — двусторонняя монета, закреплённая за персонажем. У каждой стороны — одна из трёх граней:

| Грань | Эффект |
|---|---|
| `attack` (удар) | Считается в атаку — участвует в подсчёте урона сопернику. |
| `defense` (защита) | Считается в защиту — блокирует чужую атаку. |
| `action` (действие) | Не участвует в подсчёте урона напрямую, но даёт **1 очко действия**: право перевернуть одну уже брошенную биту соперника на другую её грань. |

У персонажа несколько бит (стартовый набор задаёт `CharacterClass.starterBits`, дополнительные — покупка снаряжения типа `bit` в магазине). Грани каждой конкретной биты фиксированы (например, "удар/защита"), но при броске выпадает случайная из двух — 50/50.

Оппонент (тренировочный голем, монстр ивента) использует фиксированный шаблон из 3 бит: `[удар/защита]`, `[удар/действие]`, `[защита/защита]` (`BattleService::MONSTER_BITS`). Разные монстры пока не отличаются набором бит — только именем и HP.

---

## 2. Виды боя

| Тип | Кто участвует | Стоимость | Награда за победу |
|---|---|---|---|
| **PvE** | персонаж vs тренировочный голем | 1 очко энергии | +10 XP, +5 монет |
| **Ивент** | персонаж vs монстр активного `Event` | бесплатно | +20 XP, +15 монет |
| **Турнир** | персонаж vs персонаж, **симулируется сервером целиком за один вызов** (нет пошагового взаимодействия — см. §6) | — | чемпион турнира: +50 XP, +30 монет (только финальный победитель сетки, не за каждый матч) |
| **PvP-дуэль (`/duel`)** | персонаж vs персонаж | — | **не реализовано.** Команда `/duel` — только приглашение/подтверждение пары, реального боя за этим сейчас не следует. Это первый кандидат на "комнату боя". |

Победа в PvE/ивент-бою также засчитывается в прогресс недельного задания (`QuestService::recordBattleWin`) — но **не** для симулированных турнирных матчей.

## 3. Жизненный цикл боя

```
[СТАРТ] → ( [БРОСОК] → [ДЕЙСТВИЯ] → [ПОДСЧЁТ УРОНА] → [ПРОВЕРКА ИСХОДА] )×N → [КОНЕЦ]
              ↑___________________________________________|
                        повтор, пока бой не завершён
```

Бой (`Battle`) состоит из последовательности раундов (`BattleRound` — лог каждого сыгранного раунда: какие грани выпали, сколько урона нанесено).

### Этап 0 — Старт боя

- **PvE**: проверяется `character.energy >= 1`, при успехе списывается 1 энергии. Если энергии нет — `InsufficientEnergyException` → HTTP 409.
- **Ивент**: без проверок, энергия не тратится.
- Создаётся `Battle`: `character`, `opponentName`, `opponentHp`/`opponentMaxHp`, `status = in_progress`, `roundNumber = 0`.

### Этап 1 — Бросок (`throw`)

Одновременно для обеих сторон:
1. Для каждой биты персонажа — случайный выбор одной из двух граней.
2. Для каждой биты соперника (фиксированный шаблон, см. §1) — то же самое.
3. Результат **сохраняется на сервере** в `Battle.pendingPlayerThrows` / `pendingOpponentThrows` (а не отдаётся клиенту "на веру") — это то, что не позволяет клиенту подделать бросок, когда потом присылает выбор целей для "действия".
4. Клиенту возвращается: грани игрока, грани соперника, `playerActionCount` (сколько граней "action" выпало у игрока).

На этом этапе урон **ещё не считается** — игрок должен увидеть доску и решить, куда потратить очки действия.

### Этап 2 — Действия (только если есть `action`-грани)

- Если у игрока выпало N граней `action` — он может выбрать до N чужих (уже брошенных) бит и перевернуть их на другую грань. Индексы целей передаются в `resolve`.
- Соперник (бот) выбирает свои цели **автоматически**, эвристикой `BotActionStrategy`:
  1. Сначала переворачивает грани игрока, показывающие `attack` (снижает входящий урон — приоритет выживания).
  2. Затем — грани, показывающие `defense` (снижает защиту игрока → увеличивает урон бота).
  3. Число целей = сколько `action`-граней выпало у соперника.
- Оба набора целей выбираются **независимо и одновременно** от исходного (ещё не изменённого) броска другой стороны — не бывает так, что переворот игрока влияет на то, сколько очков действия получит бот, и наоборот.
- Если игрок не прислал `actionTargets` (или их меньше, чем очков действия) — лишние очки просто не используются.

### Этап 3 — Подсчёт урона

После применения всех переворотов финальные грани раскладываются на подсчёт:

```
playerAttack   = кол-во граней "attack" у игрока (после переворотов)
playerDefense  = кол-во граней "defense" у игрока
opponentAttack = кол-во граней "attack" у соперника
opponentDefense= кол-во граней "defense" у соперника

damageToOpponent = max(0, playerAttack  − opponentDefense)
damageToPlayer   = max(0, opponentAttack − playerDefense)
```

Грани `action` в этом подсчёте не участвуют вообще (ни в атаку, ни в защиту) — их ценность целиком в перевороте чужой биты на этапе 2.

### Этап 4 — Применение урона и проверка исхода

1. `character.hp -= damageToPlayer`, `opponent.hp -= damageToOpponent` (не уходят ниже 0).
2. `roundNumber += 1`, в БД пишется `BattleRound` (грани обеих сторон + нанесённый урон — полный лог для истории/аналитики, виден в `/admin`).
3. Исход:
   - `opponent.hp <= 0` → `status = won`. Начисляются XP/монеты (см. §2), засчитывается прогресс недельного задания.
   - `character.hp <= 0` (и `opponent.hp > 0`) → `status = lost`.
   - Иначе → бой продолжается, возврат к этапу 1 (новый бросок).
4. HP персонажа **не восстанавливается автоматически** между боями — если персонаж пришёл на бой уже раненым, он стартует с текущим HP. Лечения/отдыха в игре пока нет.

### Особые случаи

- **Одновременный нокаут** (оба HP ≤ 0 в одном раунде) — победа присуждается игроку (`opponentHp <= 0` проверяется первым в коде).
- **Затяжной бой без явного разрешения**: в режимах "авто-игры" (текстовые команды бота `/pve`, `/event-fight`, а также симуляция турнирного матча) действует потолок в **30 раундов** — если за 30 раундов никто не умер, бой останавливается, статус остаётся `in_progress`, отображается как "ничья/бой затянулся". В интерактивном режиме через Activity потолка на число раундов нет — игрок может играть сколько угодно раундов подряд, вручную нажимая "Бросить биты".

## 4. API-эндпоинты боя (что уже есть)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/battles/pve` | Начать PvE-бой (списывает энергию). |
| `POST` | `/api/events/active/battle` | Начать бой с монстром активного ивента (бесплатно). |
| `GET` | `/api/battles/{id}` | Текущее состояние боя (HP сторон, статус, `hasPendingThrow`). |
| `POST` | `/api/battles/{id}/throw` | Этап 1 — бросить биты обеих сторон, получить расклад. |
| `POST` | `/api/battles/{id}/resolve` | Этапы 2–4 — применить `actionTargets`, посчитать урон, вернуть раунд + новое состояние боя. |

`throw`/`resolve` — источник истины для UI "комнаты боя": экран должен сначала звать `throw` и анимировать раскрытие монет, дать игроку время выбрать цели (если `playerActionCount > 0`), затем звать `resolve` и анимировать результат.

Bot-эндпоинты (`/api/bot/battles/{discordId}/pve/auto`, `/api/bot/events/active/battle/auto/{discordId}`) — то же самое, но без пошагового взаимодействия: сервер сам вызывает `throw`+`resolve` в цикле с пустым `actionTargets` для игрока (только бот использует свои очки действия), пока бой не закончится или не будет достигнут потолок в 30 раундов. Это текстовый режим для Discord-команд, не для Activity.

## 5. Формула боя в псевдокоде (для справки)

```
function playRound(character, opponent):
    playerThrows   = [throwRandomFace(bit) for bit in character.bits]
    opponentThrows = [throwRandomFace(bit) for bit in opponent.bits]

    playerActionCount   = count(playerThrows, "action")
    opponentActionCount = count(opponentThrows, "action")

    # игрок присылает свои цели отдельным запросом (resolve), бот — вычисляет сам
    opponentThrows = flip(opponentThrows, playerActionTargets[:playerActionCount])
    playerThrows   = flip(playerThrows, botStrategy(playerThrows, opponentActionCount))

    dmgToOpponent = max(0, count(playerThrows,"attack")   - count(opponentThrows,"defense"))
    dmgToPlayer   = max(0, count(opponentThrows,"attack") - count(playerThrows,"defense"))

    opponent.hp   -= dmgToOpponent
    character.hp  -= dmgToPlayer

    if opponent.hp <= 0:  return WON
    if character.hp <= 0: return LOST
    return CONTINUE
```

## 6. Турнирные бои — важное отличие

Турнирные матчи (`TournamentService::simulateMatch`) используют **тот же `CombatResolver`**, но:

- Обе стороны — реальные персонажи, у обеих HP берётся `maxHp` (не текущий поврежденный HP — бой всегда начинается "по полному баку", независимо от состояния персонажа в общем мире).
- **Обе** стороны используют эвристику `BotActionStrategy` для выбора целей действия (в обычном PvE её использует только соперник-бот; здесь и "игрок", и "оппонент" матча — не интерактивные, поэтому симметрично автоматизированы).
- Бой играется **сразу до конца** (до 30 раундов) одним вызовом, без пошагового `throw`/`resolve` — результат матча известен мгновенно после запуска турнира.
- Если 30 раундов не дали победителя — судьба матча решается по остатку HP (`aHp >= bHp ? a : b`).

Это **не** живой PvP — просто "быстрый прогон" статов друг против друга, чтобы сетка турнира вообще могла существовать без реализации синхронизации двух живых игроков.

---

## 7. Чего не хватает для настоящей "комнаты боя" (PvP)

Если следующая задача — сделать реальный PvP-бой (например, через `/duel`), вот что механика раунда потребует сверху текущей PvE-схемы:

1. **Второй живой участник вместо бота.** Сейчас `throw`/`resolve` жёстко всегда считают "вторую сторону" ботом/монстром (фиксированный набор бит, автоматический выбор действия). Для PvP нужно, чтобы `Battle.opponentCharacter` мог быть реальным `Character`, а его действия — приходить от второго игрока, а не от `BotActionStrategy`.
2. **Синхронизация двух клиентов.** Оба игрока должны увидеть один и тот же бросок (этап 1) и оба — прислать свои `actionTargets` (этап 2) до того, как сервер посчитает урон (этап 3). Нужен механизм ожидания "оба игрока сделали ход" — при выбранной в проекте схеме (API-поллинг, не WebSocket) это, скорее всего, означает: `resolve` не выполняется, пока оба набора целей не получены (или не истёк таймаут хода).
3. **Тайм-аут хода** — если один из игроков не отвечает (закрыл Activity), нужно решить: авто-пропуск действия, техническое поражение, или "заморозка" боя.
4. **Комната ожидания перед боем** — сейчас `/duel` создаёт приглашение и подтверждение, но не переводит игроков в общее состояние "оба в Activity, оба готовы". Нужен отдельный статус (`pending`/`ready`/`in_progress`) и способ узнать, что оба игрока открыли арену.
5. **Идентификация "чей ход показывать"** в Activity — сейчас арена ничего не знает про второго живого игрока, только про фиксированного бота.

Существующие сущности (`Battle`, `BattleRound`, `CombatResolver`, `BitThrow`) можно переиспользовать почти без изменений — правила подсчёта урона и работы граней в PvP останутся ровно такими же, как описано в §3. Новое — это оркестрация "кто и когда ходит", а не сама боевая математика.
