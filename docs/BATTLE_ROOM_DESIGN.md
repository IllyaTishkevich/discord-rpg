# Комната боя (PvP) — дизайн

Проектирование живого PvP на основе `docs/BATTLE_RULES.md`, конкретно — раздела 7 ("Чего не хватает для настоящей комнаты боя"). Цель: два реальных игрока дерутся друг с другом через ту же боевую математику (`CombatResolver`), что уже работает для PvE/ивентов, без изменения формул урона.

Это дизайн-документ для следующей фазы реализации, код пока не пишем.

---

## 1. Что переиспользуем как есть

- **Формула урона и грани бит** — без изменений (§3, §5 `BATTLE_RULES.md`).
- **`CombatResolver::resolveRound()`** — без изменений. Он уже принимает два независимых набора бросков и один массив `actionTargets` для "player"-стороны; для PvP вторая сторона просто перестаёт быть ботом (`BotActionStrategy`) — её `actionTargets` тоже будут приходить от реального игрока.
- **`Battle` / `BattleRound`** — расширяем, не переписываем (см. §3).
- **Схема `throw` → `resolve`** — концептуально та же, но `resolve` для PvP разделяется на "каждая сторона присылает свои цели независимо" (см. §4).

## 2. Ключевая проблема: у боя два живых зрителя

Сейчас `Battle` асимметричен: есть `character` ("я") и "противник" как статы монстра, без своего аккаунта. Для PvP обе стороны — настоящие `Character`, и **каждый из двух игроков должен видеть бой со своей колокольни** ("я" / "соперник" должны инвертироваться в зависимости от того, кто спрашивает).

**Решение: не дублировать `Battle` на двух игроков, а сериализовать с учётом зрителя.**

```
BattleSerializer::battleForViewer(Battle $battle, Character $viewer): array
```

Если `viewer === battle.character` → всё как сейчас. Если `viewer === battle.opponentCharacter` → поля `character`/`opponent` в JSON меняются местами (включая исход `won`/`lost` — он тоже переворачивается). Существующий метод `battle()` остаётся для PvE/ивентов (где зритель всегда один — `battle.character`), новый `battleForViewer()` используется всегда, когда `battle.mode === pvp`.

## 3. Изменения модели данных

### `Battle` — новые поля

```
mode: enum('pve' | 'event' | 'pvp')           -- явный тип вместо угадывания по event/opponentCharacter
opponentCharacter: ?Character (nullable FK)    -- задан только при mode = pvp
characterReady: bool (default true)            -- true сразу для pve/event; для pvp — пока игрок не зашёл в Activity
opponentReady: bool (default true)             -- аналогично для второй стороны
opponentAccepted: bool (default true)          -- аналогично; для pvp — пока не нажата "Принять" в Discord
pendingCharacterActionTargets: ?array (json)   -- цели действия "моей" стороны в текущем раунде (только pvp)
pendingOpponentActionTargets: ?array (json)    -- цели действия второй стороны (только pvp)
roundDeadlineAt: ?DateTimeImmutable            -- дедлайн текущего раунда (только pvp, см. §6)
```

`opponentName` / `opponentHp` / `opponentMaxHp` остаются как есть и используются только при `mode ∈ {pve, event}`. При `mode = pvp` источник HP соперника — `opponentCharacter.getHp()`/`getMaxHp()` напрямую (то же самое поле, что уже используется как "живое" HP персонажа везде в игре — никакого отдельного "боевого HP" не вводим, урон в PvP так же необратимо остаётся на персонаже после боя, как и в PvE).

### `BattleStatus` — новое значение

```
waiting       -- бой создан (вызов брошен), но не оба игрока готовы к раунду
in_progress   -- как сейчас
won / lost    -- как сейчас, трактуется относительно battle.character (сериализатор инвертирует для второго зрителя)
abandoned     -- новое: вызов отклонён, либо один из игроков не вышел на бой/отключился до первого раунда
```

Никаких новых сущностей (`DuelInvite`, `DuelRoom` и т.п.) не заводим — `Battle` в статусе `waiting` **и есть** приглашение/лобби. Один источник истины на весь жизненный цикл: вызов → лобби → бой → результат.

### Миграция

Новые колонки все nullable/со значением по умолчанию — обратно совместимо с уже существующими PvE/ивент-боями (у них `mode` проставится `pve`/`event` при миграции данных, `opponentCharacter` остаётся `null`).

## 4. Синхронизация раунда

Сейчас `resolve` — одна сторона (реальный игрок) присылает `actionTargets`, вторая (бот) считается синхронно внутри того же вызова через `BotActionStrategy`. Для PvP обеим сторонам нужно **независимо** прислать свои цели до подсчёта урона.

### Новый эндпоинт: `POST /api/battles/{id}/submit-actions`

Тело: `{ actionTargets: number[] }`. Только для `mode = pvp`.

1. Сервер определяет, какая сторона зовёт (по `character.user === текущий пользователь` либо `opponentCharacter.user === текущий пользователь`).
2. Сохраняет присланные цели в `pendingCharacterActionTargets` или `pendingOpponentActionTargets` (в зависимости от стороны).
3. Если **обе** стороны уже прислали свои цели — сразу вызывает `CombatResolver::resolveRound()` с обоими реальными наборами (никакого `BotActionStrategy` в PvP нет вообще), пишет `BattleRound`, применяет урон, проверяет исход, очищает pending-поля.
4. Если прислала только одна сторона — просто сохраняет и возвращает `{ waitingForOpponent: true }`.

Существующий `POST /api/battles/{id}/resolve` остаётся **только** для `mode ∈ {pve, event}`; вызов его на PvP-бою — `409` с понятной ошибкой ("используйте submit-actions").

`POST /api/battles/{id}/throw` остаётся как есть по сигнатуре, но для PvP:
- бросать может любая из сторон (обычно инициируется автоматически сервером сразу после того, как раунд разрешился, либо сразу после того, как обе стороны стали `ready`);
- вызов идемпотентен в рамках раунда — если бросок уже случился, повторный вызов просто возвращает уже брошенный результат, а не перебрасывает кости (важно: оба клиента могут дёрнуть `throw`, гонка не должна давать разные результаты двум игрокам).

### `GET /api/battles/{id}` — новое поле для PvP

`opponentSubmitted: bool` — прислал ли соперник уже свои цели в текущем раунде (чтобы UI мог показать "Ждём соперника..." вместо зависшего спиннера).

## 5. Жизненный цикл боя целиком

```
/duel @user (Discord)
        │
        ▼
 [WAITING]  Battle создан: character=инициатор, opponentCharacter=цель,
            opponentAccepted=false, characterReady=false, opponentReady=false
        │
        │  цель нажимает "Принять" в Discord
        ▼
 [WAITING]  opponentAccepted=true
            (оба игрока получают инструкцию открыть Activity)
        │
        │  оба игрока независимо открывают Activity → видят экран лобби
        │  → жмут "Готов" → join() выставляет свой *Ready=true
        ▼
 [WAITING] → когда characterReady && opponentReady && opponentAccepted:
            статус → IN_PROGRESS, сервер сразу делает первый throw
        │
        ▼
 [IN_PROGRESS]  цикл раунда:
   throw (авто) → оба видят расклад →
   submit-actions (обе стороны, независимо, в любом порядке) →
   как только обе пришли (или истёк roundDeadlineAt) → resolve →
   применяется урон → если никто не умер → снова throw
        │
        ▼ (HP одной из сторон ≤ 0)
 [WON / LOST]  сериализуется по зрителю (§2); прогресс недельного
               задания и награды — по аналогии с PvE (нужно решить:
               сумма наград для PvP, см. §8 "Открытые вопросы")

 Ветка отказа: "Отклонить" в Discord, либо один из игроков не
 подтверждает готовность за разумное время → [ABANDONED], бой закрыт,
 HP никто не теряет.
```

## 6. Таймаут хода

Инфраструктура проекта сознательно без WebSocket/воркеров (см. `README.md`, "API-поллинг + оптимистичный UI"), поэтому таймаут реализуем **лениво**, без фоновых задач:

- При каждом `throw` выставляется `roundDeadlineAt = now + 30s` (число обсуждаемо, 30с — отправная точка).
- Любой вызов `GET /battles/{id}` или `submit-actions`, обнаруживший `now > roundDeadlineAt` и то, что одна из сторон ещё не прислала цели — сам достраивает недостающий `actionTargets = []` и вызывает разрешение раунда, как если бы опоздавшая сторона решила не использовать очки действия. Раунд не подвисает даже если ни один клиент активно не поллит в этот момент — он досчитается при следующем же обращении любого из двух игроков (или бота через `/api/bot/...`, если понадобится диагностика).
- Итог: никакой отдельный cron/воркер не нужен — таймаут проверяется "по требованию", в духе уже принятого решения по синхронизации боя.

Полное отсутствие ответов (оба клиента закрыли Activity) — раунд просто не досчитывается, пока кто-то не откроет её снова. Это приемлемо для MVP; форс-мажорный автоматический разбор "оба пропали" — не в этой итерации (см. §8).

## 7. Изменения в Activity и боте

### Bot

- `/duel @user` перестаёт быть чисто Discord-эффектом: теперь дёргает **новый bot-эндпоинт** `POST /api/bot/battles/pvp` (тело: discordId инициатора + цели) → создаёт `Battle(mode=pvp, status=waiting)`, возвращает `battleId`.
- Кнопка **"Принять"** зовёт `POST /api/bot/battles/{id}/accept` (bot-secret) — выставляет `opponentAccepted=true`; сообщение обновляется на "Оба открывайте Activity (/play), чтобы начать бой".
- Кнопка **"Отклонить"** зовёт `POST /api/bot/battles/{id}/decline` → `status=abandoned`.

### Activity

- Новый экран **`DuelLobbyScreen`**: если у игрока есть незавершённый PvP-бой в статусе `waiting`/`in_progress` (проверяется новым эндпоинтом типа `GET /api/battles/my-active-pvp`, вызывается сразу после логина, аналогично тому, как сейчас проверяется активный ивент), показывает имя соперника и кнопку "Готов" (→ `join`), либо сразу переводит в `ArenaScreen`, если бой уже `in_progress`.
- **`ArenaScreen`** получает флаг `isPvp`. Отличия при `isPvp = true`:
  - кнопки "Бросить биты" нет — бросок уже случился автоматически, экран просто поллит `GET /battles/{id}` до появления `hasPendingThrow`;
  - "Разрешить раунд" зовёт `submit-actions`, а не `resolve`;
  - после отправки своих целей — состояние "Ждём соперника..." (используя новое поле `opponentSubmitted`), автоматический переход к результату раунда, как только сервер досчитал (обнаруживается очередным поллом).
- **`BattleResultScreen`** — без изменений, просто получает перспективно-корректные данные от `battleForViewer()`.

## 8. Открытые вопросы (нужно решить перед реализацией)

1. **Награды за PvP-победу.** В PvE/ивентах чёткие числа (§2 `BATTLE_RULES.md`). Для дуэли — то же самое (фикс. XP/монеты победителю), или ставка (проигравший теряет часть монет, победитель забирает)? Ставки эффектнее, но требуют защиты от "слива" (два своих аккаунта договариваются, кто проигрывает, чтобы фармить монеты).
2. **Лимит дуэлей в день** — PvE ограничен энергией, ивенты бесплатны без лимита (это ок, так как ивент разовый и ограничен по времени). Нужно ли ограничивать PvP так же, как PvE (тратить энергию), чтобы не фармить недельное задание "win_battles" дуэлями между двумя своими же аккаунтами?
3. **Что считать таймаутом целиком** (оба игрока пропали посреди боя, не только один раунд) — оставить бой вечно висящим в `in_progress`, или автоматически завершать по бездействию (например, через `finishedAt`-подобную проверку "нет активности N минут → abandoned")? Для MVP предлагаю не решать явно — зависшие PvP-бои видно и чистить руками через `/admin` (Battle уже полностью доступен там, см. `docs/PRODUCTION_SETUP.md` / предыдущую работу над `/admin`).
4. **Реванш / очередь матчей** — вне рамок этого документа, чистый MVP-инкремент.

## 9. План внедрения (фазы)

1. **Данные**: новые поля `Battle` + `BattleStatus::Waiting/Abandoned` + миграция.
2. **Бэкенд-синхронизация**: `submit-actions`, `battleForViewer()`, ленивый таймаут, разделение `resolve` на pve/event-only.
3. **Бот**: `/api/bot/battles/pvp`, `accept`/`decline`, переписанный `/duel`.
4. **Activity**: `DuelLobbyScreen`, адаптация `ArenaScreen` под `isPvp`.
5. **Полировка**: обработка обрыва связи, решения по §8.

Каждая фаза самостоятельно тестируема через `curl` тем же способом, что и весь остальной бэкенд в этом проекте (см. предыдущие спринты) — живой Discord для проверки серверной части не нужен.
