# Боевая система v2: приоритет и пошаговый обмен ударами — дизайн

Статус: **реализовано для всех режимов, включая PvP — полноценный пошаговый интерактивный бой везде (§1–§8).** Описывает замену старого алгоритма подсчёта раунда (`docs/BATTLE_RULES.md` §3: одновременный бросок → одновременный подсчёт `attack − defense`) на пошаговый обмен активациями бит с приоритетом хода. Причина — запрос пользователя: добавить новую характеристику грани "преимущество", которая определяет очерёдность хода в раунде, и заменить одновременный подсчёт урона на последовательный обмен, где атака гасится защитой оппонента 1:1, а не одной большой формулой в конце. PvP изначально оставался на старом одновременном движке (`CombatResolver`) дольше остальных режимов — см. §7 про то, что для этого потребовалось.

**Реализация (боевая математика, §1–§6):** `App\Battle\ExchangeResolver` (+ `Move`, `Exchange`, обновлённые `Bit`/`BitThrow`/`Equipment` с полями `advantage*`). Используется неинтерактивным автобоем (bot text commands, симуляция турнира — весь раунд одним вызовом) и как эталонная логика для интерактивного движка. Тесты: `tests/Battle/ExchangeResolverTest.php`. Одно осознанное упрощение: способность **Reroll** не перебрасывает сам жетон, только что потраченный на её оплату (см. пометку в §5) — с точки зрения геймплея неотличимо, так как лицо потраченного жетона больше нигде не читается.

**Реализация (интерактивный пошаговый бой, §7–§8):** `App\Battle\InteractiveExchangeEngine` + `ExchangeRoundState` (состояние раунда между запросами, хранится в `Battle.pendingExchangeState`) + `BattleService::submitExchangeMove()` (PvE/ивент, бот отвечает синхронно) / `submitPvpExchangeMove()` (PvP, обе стороны реальные — отдельные запросы, `turnForSide()`/`submitPvpLead()`/`passPvpLead()`/`submitPvpRespond()`, плюс тайм-аут на ход `applyPvpMoveTimeoutIfExpired()`) + эндпоинт `POST /battles/{id}/exchanges/move`. Фронтенд — единый `activity/src/screens/ArenaScreen.tsx` для всех режимов, с поллингом `GET /{id}` пока `turn === "wait"` (только PvP). Тесты: `tests/Battle/InteractiveExchangeEngineTest.php`.

`CombatResolver`/`BotActionStrategy`/`resolveRoundLegacy()`/`submit-actions` удалены — были PvP-only и стали не нужны, когда PvP перешёл на интерактивный движок.

**Множитель грани (§1bis, реализовано позже §1–§8):** `Bit`/equipment-биты получили `multiplierA`/`multiplierB: int` (по умолчанию 1) — сколько урона/блока/очков действия стоит эта грань, вместо фиксированной 1 за биту. См. §1bis ниже.

## 1. Новая характеристика грани: "преимущество"

`BitFace` (грань — `attack`/`defense`/`action`) остаётся как есть. К этому добавляется **независимый булевый флаг** на каждой конкретной стороне каждой конкретной биты: `advantage: bool`. То есть у грани есть две независимые характеристики — тип (attack/defense/action) и наличие преимущества. Например, бита может быть `[удар+преимущество / защита]` — при выпадении удара игрок дополнительно получит очко преимущества, при выпадении защиты — нет.

**Модель данных** (`backend/src/Entity/Bit.php`):
- `faceA: BitFace`, `faceB: BitFace` — как сейчас.
- Новое: `faceAAdvantage: bool`, `faceBAdvantage: bool` — по умолчанию `false`.
- Нужна миграция Doctrine (два новых `boolean NOT NULL DEFAULT false` столбца в таблице `bit`).
- `BitThrow` (value object броска) добавляет `advantage: bool` рядом с `thrownFace`.
- Сид-команды (`SeedCharacterClassesCommand`, снаряжение с новыми битами) и EasyAdmin `BitCrudController` — обновить, чтобы преимущество можно было проставить у стартовых бит/предметов магазина.

## 1bis. Множитель грани

Независимо от "преимущества" (§1), каждая грань каждой конкретной биты несёт **множитель**: `multiplierA`/`multiplierB: int`, по умолчанию `1`. Работает одинаково для всех типов граней — атака наносит урон, равный множителю (а не 1 за активацию), защита блокирует столько же атаки, действие даёт столько же очков действия (в том числе на стоимость способностей — см. §5). Например, бита `[удар ×2 / защита]` при выпадении удара наносит 2 урона одной активацией, как если бы игрок активировал две обычные биты-удара разом.

**Модель данных**: `Bit::$multiplierA`/`$multiplierB` (int, `Assert\Positive`), `BitThrow::$multiplierA`/`$multiplierB`/`$thrownMultiplier` (травится по той же схеме, что advantage — `flipped()` меняет сторону, множитель следует за гранью). `Equipment::$bitMultiplierA`/`$bitMultiplierB` — та же характеристика для бит, выдаваемых снаряжением.

**Боевая математика**: раньше формулы `leaderAttack`/`leaderDefense`/`responderAttack`/`responderDefense` в `ExchangeResolver`/`InteractiveExchangeEngine` брались напрямую из количества активированных бит (`Move::$count`). Теперь `Move`/внутренние структуры хода различают:
- `count` — сколько именно битовых объектов активировано (нужно только чтобы правильно пометить их как использованные);
- `amount` — сумма множителей этих бит (реально участвует в подсчёте урона/блока/очков действия).

Для бота (`chooseLeadMove`/`chooseResponseMove` в обоих движках) появился общий хелпер `gatherByFace()` (`ExchangeResolver`/`ExchangeRoundState`) — жадно набирает неиспользованные биты нужной грани, при ответе — пока не наберёт хотя бы столько же `amount`, сколько у входящей атаки (может набрать чуть больше — недобор всегда хуже перебора, а частично активировать биту нельзя).

**Побочный баг, найденный при этой работе** (не связан напрямую с множителем, но стал заметен из-за него): `InteractiveExchangeEngine::validateAndConsumeMove()` помечал использованными "первые N неиспользованных бит этой грани", а не именно те индексы, которые выбрал игрок — раньше это было незаметно (все биты одной грани были взаимозаменяемы), но с разными множителями на битах одной грани выбранная игроком бита могла остаться доступной, а другая, нетронутая — уйти в тень. Исправлено: помечаются именно выбранные индексы.

**UI**: множитель отображается прямо на монете биты (`BitCoin.tsx`) маленьким бейджем `×N` в углу — только когда множитель больше 1. Пробрасывается через `ThrowResult`/`ExchangeMoveResult` (`playerMultipliers`/`opponentMultipliers`, тот же порядок индексов, что и `playerFaces`/`opponentFaces`) и `GET /battles/{id}`'s поле `exchange` (для PvP-поллинга).

## 2. Приоритет хода

После броска (этап 1, без изменений) для каждой стороны считается:

```
playerAdvantageCount   = count(playerThrows, advantage == true)
opponentAdvantageCount = count(opponentThrows, advantage == true)
```

- Кто набрал **больше** очков преимущества — ходит первым в этом раунде (становится "ведущим", opponent — "отвечающим").
- **Ничья** — первый ход определяется случайно (50/50), независимо от того, кто ходил первым в предыдущем раунде.
- Каждый новый раунд (новый бросок) пересчитывает преимущество и, соответственно, ведущего заново — лидерство не переносится между раундами.

## 3. Пошаговый обмен ("обмен" = один шаг цикла ниже)

Раунд теперь — это не единственный подсчёт, а последовательность **обменов**, продолжающаяся, пока у одной из сторон не закончатся ещё не задействованные (не активированные) биты этого броска.

```
пока у ОБЕИХ сторон есть хотя бы одна неактивированная бита:
    1. Ведущий выбирает ОДНУ ИЛИ НЕСКОЛЬКО своих неактивированных бит ОДНОГО типа
       (все "attack", либо все "defense", либо все "action") и активирует их —
       это его ход в этом обмене.
    2. Отвечающий видит, что выбрал ведущий, и в ответ может (по желанию)
       активировать любое количество СВОИХ неактивированных бит (любого
       типа, тоже все одного типа за раз — то же правило "группами").
       Можно не отвечать вовсе (0 бит).
    3. Обмен разрешается (см. §4).
    4. Роль ведущего переходит другой стороне — второй игрок ведёт
       следующий обмен (простое чередование хода внутри раунда: 1-2-1-2…,
       начиная с определённого в §2 приоритета).
```

Как только у **одной** из сторон не осталось неактивированных бит броска — она больше не может ни вести, ни отвечать. Другая сторона продолжает вести обмены **в одиночку** (без ответа — по правилу §4 "нет ответа = полный урон") своими оставшимися битами, пока и они не закончатся. Только когда биты кончились у **обеих** сторон, раунд завершается. Начинается новый раунд с нового броска (этап 1). *(Исправлено: изначально было "раунд заканчивается, как только опустеет одна сторона" — это баг, поймано на реальном плейтесте.)*

## 4. Разрешение одного обмена

Пусть ведущий активировал `L` бит типа `T_L`, отвечающий — `R` бит типа `T_R` (`R` может быть 0, если не ответил).

- **attack vs defense** (в любом порядке — атаку блокирует защита независимо от того, кто из двоих вёл этот конкретный обмен, ведущий определяет только очерёдность **хода**, а не то, "чья атака приоритетнее"):
  - Каждая защита гасит одну атаку 1:1.
  - Если атак больше, чем защит — разница проходит уроном (по 1 урону за не заблокированную атаку).
  - Если защит больше или равно — урона нет (лишние защиты просто не используются, не переносятся на другие обмены).
- **attack vs attack** (оба выбрали "attack" — отвечающий не стал блокировать, а тоже атаковал): урон проходит **в обе стороны одновременно**, по числу активированных атак каждой стороны (никто никого не блокирует).
- **attack vs (нет ответа)**: вся активированная атака проходит полным уроном (см. предыдущий вопрос — договорились, что отсутствие ответа = отсутствие защиты).
- **defense vs что угодно, когда никто не атаковал** (ведущий сам решил "походить" защитой без непосредственной угрозы — редкий, но не запрещённый случай): эффекта нет, защита просто активирована и выбывает из пула на этот раунд без последствий (защита не накапливается на будущее — не имеет смысла играть "в пустоту", но правилами не запрещено).
- **action vs что угодно**: активированная "action"-бита не участвует в подсчёте урона напрямую — она увеличивает счётчик очков действия соответствующей стороны на 1 (то же значение, что раньше считалось по всем `action`-граням брошенных бит сразу). Способности (см. §5) списывают эти очки, когда игрок явно выбирает способность — активация action-биты сама по себе ничего не активирует, только "копит" ресурс.

Урон применяется к HP сразу по итогам обмена (не откладывается до конца раунда) — так же, как и раньше, `character.hp -= damageToPlayer` и т.д., просто теперь это происходит несколько раз за раунд (по разу на обмен), а не один раз в конце.

## 5. Способности (переворот/неблокируемый урон/переброс/зеркало) — не меняются концептуально

Существующие 4 способности (`docs/BATTLE_RULES.md` §3.1) остаются как есть — они списывают накопленные очки действия (§4, action-активации) на весь **раунд целиком**, не на конкретный обмен. Это значит:

- Игрок объявляет выбор способности **один раз за раунд** (как сейчас), но действовать она может, только когда у него накопилось нужное количество очков действия из уже проведённых обменов этого раунда — то есть выбор способности логично делать **после** того, как все свои `action`-биты уже активированы (иначе нечем платить).
- `AbilityResolver` не меняется по сути, меняется только момент вызова: раньше он получал сразу все брошенные грани и считал `action`-очки по ним; теперь `action`-очки нужно считать по **уже активированным** action-битам за раунд (переменная, растущая по ходу обменов), а не по всему броску сразу.
- Способность `flip` (переворот) нацелена на биты соперника — раньше это были "уже брошенные, но ещё не посчитанные" биты; теперь логичнее всего нацеливать её на **ещё не активированные** биты соперника (те, что ещё не сыграли в этом раунде) — переворачивать уже сыгранную (активированную и учтённую в уроне) биту бессмысленно, обмен уже разрешён.
- **Открытый вопрос** (рекомендация, не блокер): разрешить активировать способность как **отдельный тип хода** в обмене (наравне с attack/defense/action) — то есть в момент, когда у игрока есть накопленные action-очки, он может в свой ход вместо активации бит объявить "использую способность X" вне очереди обычных бит. Это самый гибкий вариант и не требует отдельного протокола поверх обменов. **Принято** — реализовано именно так: активация `action`-бит немедленно применяет способность (если хватает "стоимости" — `AbilityType::fixedCost()`), лишние очки в том же ходе используются как обычный переворот; после первого срабатывания способности за раунд дальнейшие `action`-ходы той же стороны тоже становятся обычным переворотом.
- **Зеркало урона** реализовано так, что оно отражает урон, полученный **в том же обмене**, где было активировано (а не только в последующих) — это самый естественный и просто реализуемый вариант; отдельно не уточнялось.

## 6. PvE/бот и авто-бой

`BotActionStrategy` (сейчас — эвристика выбора целей для flip) расширяется до **эвристики ведения обмена**: когда ход бота (как ведущего или отвечающего), бот должен решить:
- Что активировать первым (эвристика: атаковать, если есть чем, иначе защищаться, если под угрозой, иначе копить action).
- Как отвечать на ход игрока (эвристика: если игрок атакует и у бота есть defense — блокировать; если нет — атаковать в ответ, если есть чем).

Для текстового авто-боя (`/pve`, `/event-fight`, симуляция турнирного матча) — цикл обменов прогоняется полностью на сервере за один HTTP-вызов, как и раньше весь раунд целиком; итоговый лог обменов можно свернуть в те же поля `BattleRound` (или расширить `BattleRound`, чтобы хранить список обменов раунда для истории/отладки — см. §8).

## 7. Интерактивный пошаговый бой — реализовано для всех режимов

**Статус: реализовано для всех режимов, включая PvP.** В отличие от изначального плана ("сначала обкатать на автобое, интерактивность — потом"), пошаговый интерактивный бой сразу сделан для PvE/ивента — именно так, как просил пользователь: бросок → определяется, кто ходит первым → ведущий выбирает одну биту (или несколько одинаковых) → если это действие, сразу предлагается выбрать способность → отвечающий (бот — автоматически, мгновенно) реагирует → урон применяется немедленно → очередь переходит другой стороне → повтор, пока у обеих сторон не кончатся биты. PvP получил тот же протокол позже отдельным заходом (см. ниже) — единственная разница в том, что "отвечающая" сторона теперь может быть реальным вторым игроком, а не ботом.

Реализация: `App\Battle\InteractiveExchangeEngine` — тот же движок, что и `ExchangeResolver`, но как возобновляемая машина состояний (`ExchangeRoundState`, хранится в JSON на `Battle.pendingExchangeState` между запросами), а не как функция "посчитать весь раунд за один вызов".

### PvE/ивент (бот всегда ходит мгновенно)

Поскольку тут всего две стороны и бот всегда ходит эвристикой мгновенно, реальный сетевой обмен нужен только когда очередь доходит до игрока:

- `POST /battles/{id}/throw` — дополнительно возвращает `turn` (`"lead"` или `"respond"`) и, если это ответ, `incomingMove` — что уже разыграл бот, если он повёл первым (бот-ход при этом уже мгновенно применён на сервере).
- `POST /battles/{id}/exchanges/move`, тело `{ indices: number[], ability?, targets? }`. Сервер сам определяет по своему состоянию, ведёт сейчас игрок или отвечает — не доверяет клиенту. Пустой `indices` при ответе означает "пропустить" (правило §4: нет ответа = полный урон).
- Ответ содержит `newExchanges` (что разрешилось за этот вызов — может быть несколько обменов сразу, если бот доигрывает соло после того, как у игрока кончились биты), актуальные `playerFaces`/`opponentFaces` (грани могут меняться по ходу раунда через переворот) и `playerUsed`/`opponentUsed` (какие биты уже неактивны до следующего броска), плюс `roundComplete` и, если раунд завершён, — `round` (полная запись раунда с логом обменов) и обновлённое состояние `battle` (HP применяется сразу за каждый обмен, а не пачкой в конце — если кто-то потерял всё HP посреди раунда, бой обрывается сразу же, не доигрывая оставшиеся обмены).

### PvP (обе стороны реальные — тот же эндпоинт, другая внутренняя логика)

Ключевое отличие от PvE: никто не может "мгновенно доиграть" ход живого человека, как за бота — значит, движок не может разрешить обмен целиком за один вызов, когда ведёт реальный игрок (в отличие от `submitLead()`, который для PvE тут же считает и ответ бота). Решение — генерализовать движок под "любая сторона может быть ведущим/отвечающим", вместо жёсткого "player всегда ведёт и получает мгновенный ответ, bot всегда отвечает":

- `InteractiveExchangeEngine::startPvpRound()` — как `startRound()`, но без автоигры: даже если по преимуществу должен вести "opponent"-сторона (в PvP это просто вторая сторона, не бот), она всё равно обязана прислать ход явно.
- `turnForSide(state, isPlayerSide)` — версия `currentTurn()` для конкретной стороны, с четвёртым значением `'wait'` (сейчас не твоя очередь). `currentTurn()` для PvE это различие никогда не наблюдало, так как бот доигрывает до реальной точки принятия решения раньше, чем клиент успевает спросить.
- `submitPvpLead()` — в отличие от `submitLead()`, только фиксирует ведущий ход и **приостанавливается** (не считает ответ — отвечать будет отдельный запрос от второй реальной стороны). `passPvpLead()` — отказ от инициативы без траты бит (используется как реакция на истечение тайм-аута хода, см. ниже, но не завязан на это жёстко).
- `submitPvpRespond()` — как `submitRespond()`, но с явным параметром "какая сторона отвечает", а не жёстко "player".
- `BattleService::submitPvpExchangeMove()` — оркестрация поверх этих методов: определяет `isPlayerSide` через `requireSide()`, никакого цикла автодоигровки за бота (его просто нет).
- Тайм-аут хода — `applyPvpMoveTimeoutIfExpired()`, лениво проверяется на каждый relevant запрос (и на `submitPvpExchangeMove()`, и на чтение `GET /{id}` через `syncPvpExchangeState()`), тот же принцип "без воркера", что и у остального проекта (см. `docs/BATTLE_ROOM_DESIGN.md` §6). Не ответил вовремя = полный урон от входящего хода; не повёл вовремя = инициатива переходит другой стороне.
- Один нетривиальный баг, пойманный юнит-тестом, а не вручную: `ExchangeRoundState::isOver()` проверял только количество непотраченных бит — для PvE это всегда корректно (бот никогда не оставляет мяч в воздухе, когда у отвечающего кончились биты, см. `autoAdvance()`'s `remainingCount(true) > 0` guard), но для PvP ведущий ход может исчерпать биты **обеих** сторон разом, а ответ ещё не пришёл. `isOver()` теперь дополнительно требует `pendingLeaderMove === null`.
- `GET /battles/{id}` — для PvP дополнительно отдаёт `exchange` (снимок текущего незавершённого обмена в перспективе зрителя, тот же формат, что throw/move) или `null`, если обмена нет. Это то, что поллит клиент, чей сейчас черёд ждать.

Что осталось от старого черновика протокола (`exchanges`/`exchanges/{id}/respond` как отдельные REST-ресурсы, поллинг `pendingExchange`) — не реализовано буквально, вместо этого переиспользован уже существующий эндпоинт `exchanges/move` (сервер сам понимает "лидируешь ты или отвечаешь" по стороне вызывающего и состоянию), а поллинг встроен в уже существующий `GET /{id}`.

## 8. Activity UI — реализовано (все режимы)

Единый `ArenaScreen` для PvE/ивента и PvP (`PvpArenaScreen` с отдельным интерфейсом "выбор способности разом на весь раунд" удалён — слился в один компонент):
- После броска показывается, чей сейчас ход: если ваш — выбор группы одинаковых бит для активации (клик по монетам, разные грани нельзя смешивать в одном ходе); если сторона уже походила — показывается, что именно она разыграла, с кнопками "ответить" или "не отвечать". Для PvP, пока ход соперника (`turn === "wait"`), экран поллит `GET /{id}` каждые 2 секунды вместо показа кнопок выбора.
- Если выбранные биты — грань "действие", после подтверждения выбора бит отдельным шагом предлагается выбрать способность (и цели для переворота, если выбран "Переворот") — ровно как описано в исходном сценарии; список доступных способностей отфильтрован по тому, что реально разрешено персонажу (класс/личное/снаряжение).
- Уже активированные в этом раунде биты остаются на экране, но визуально гаснут (`bit-coin--used`) и больше не кликабельны — вместо того чтобы прятать их за "?".
- Лог обменов показывается построчно и накапливается по ходу раунда в реальном времени (не одной строкой урона в конце), например: "Ты: удар ×3 → Соперник: защита ×1 — −2 сопернику". При завершении раунда лог перезаписывается авторитетной версией с сервера (`round.exchanges`) — для PvP локально накопленный лог мог не увидеть ходы, сделанные соперником пока клиент ждал.

## 9. Что НЕ меняется

- Сам бросок бит (этап 1, случайность 50/50 на грань) — без изменений.
- 4 боевые способности по сути — без изменений, меняется только момент подсчёта action-очков (§5).
- Общая структура сущностей `Battle`/`BattleRound`/`Bit` — расширяется, не переписывается с нуля.
- HP/энергия/награды/турниры/ивенты — не затрагиваются этим документом.
