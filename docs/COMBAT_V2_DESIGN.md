# Боевая система v2: приоритет и пошаговый обмен ударами — дизайн

Статус: **реализовано для PvE/ивент/турнир (§1–§6).** PvP всё ещё на старом движке — см. §7. Описывает замену текущего алгоритма подсчёта раунда (`docs/BATTLE_RULES.md` §3: одновременный бросок → одновременный подсчёт `attack − defense`) на пошаговый обмен активациями бит с приоритетом хода. Причина — запрос пользователя: добавить новую характеристику грани "преимущество", которая определяет очерёдность хода в раунде, и заменить одновременный подсчёт урона на последовательный обмен, где атака гасится защитой оппонента 1:1, а не одной большой формулой в конце.

**Реализация:** `App\Battle\ExchangeResolver` (+ `Move`, `Exchange`, обновлённые `Bit`/`BitThrow`/`Equipment` с полями `advantage*`). Подключено в `BattleService::computeAndApplyRound()` (только когда `!$battle->isPvp()`) и в `TournamentService::simulateMatch()`. PvP по-прежнему считается через `CombatResolver` (вынесено в `BattleService::resolveRoundLegacy()`). Тесты: `tests/Battle/ExchangeResolverTest.php`. Одно осознанное упрощение относительно текста ниже: способность **Reroll** не перебрасывает сам жетон, только что потраченный на её оплату (см. пометку в §5) — с точки зрения геймплея неотличимо, так как лицо потраченного жетона больше нигде не читается.

Этот документ фиксирует точный алгоритм **перед** тем, как переписывать `CombatResolver`/`BattleService`/Activity — чтобы не переделывать реализацию из-за недосказанностей в правилах.

## 1. Новая характеристика грани: "преимущество"

`BitFace` (грань — `attack`/`defense`/`action`) остаётся как есть. К этому добавляется **независимый булевый флаг** на каждой конкретной стороне каждой конкретной биты: `advantage: bool`. То есть у грани есть две независимые характеристики — тип (attack/defense/action) и наличие преимущества. Например, бита может быть `[удар+преимущество / защита]` — при выпадении удара игрок дополнительно получит очко преимущества, при выпадении защиты — нет.

**Модель данных** (`backend/src/Entity/Bit.php`):
- `faceA: BitFace`, `faceB: BitFace` — как сейчас.
- Новое: `faceAAdvantage: bool`, `faceBAdvantage: bool` — по умолчанию `false`.
- Нужна миграция Doctrine (два новых `boolean NOT NULL DEFAULT false` столбца в таблице `bit`).
- `BitThrow` (value object броска) добавляет `advantage: bool` рядом с `thrownFace`.
- Сид-команды (`SeedCharacterClassesCommand`, снаряжение с новыми битами) и EasyAdmin `BitCrudController` — обновить, чтобы преимущество можно было проставить у стартовых бит/предметов магазина.

## 2. Приоритет хода

После броска (этап 1, без изменений) для каждой стороны считается:

```
playerAdvantageCount   = count(playerThrows, advantage == true)
opponentAdvantageCount = count(opponentThrows, advantage == true)
```

- Кто набрал **больше** очков преимущества — ходит первым в этом раунде (становится "ведущим", opponent — "отвечающим").
- **Ничья** — первый ход определяется случайно (50/50), независимо от того, кто ходил первым в предыдущем раунде.
- Каждый новый раунд (новый бросок) пересчитывает преимущество и, соответственно, ведущего заново — лидерство не переносится между раундами.

## 3. Пошаговый обмен ("обмен" = один шаг цикла ниже)

Раунд теперь — это не единственный подсчёт, а последовательность **обменов**, продолжающаяся, пока у одной из сторон не закончатся ещё не задействованные (не активированные) биты этого броска.

```
пока у ОБЕИХ сторон есть хотя бы одна неактивированная бита:
    1. Ведущий выбирает ОДНУ ИЛИ НЕСКОЛЬКО своих неактивированных бит ОДНОГО типа
       (все "attack", либо все "defense", либо все "action") и активирует их —
       это его ход в этом обмене.
    2. Отвечающий видит, что выбрал ведущий, и в ответ может (по желанию)
       активировать любое количество СВОИХ неактивированных бит (любого
       типа, тоже все одного типа за раз — то же правило "группами").
       Можно не отвечать вовсе (0 бит).
    3. Обмен разрешается (см. §4).
    4. Роль ведущего переходит другой стороне — второй игрок ведёт
       следующий обмен (простое чередование хода внутри раунда: 1-2-1-2…,
       начиная с определённого в §2 приоритета).
```

Как только у **одной** из сторон не осталось неактивированных бит броска — она больше не может ни вести, ни отвечать. Другая сторона продолжает вести обмены **в одиночку** (без ответа — по правилу §4 "нет ответа = полный урон") своими оставшимися битами, пока и они не закончатся. Только когда биты кончились у **обеих** сторон, раунд завершается. Начинается новый раунд с нового броска (этап 1). *(Исправлено: изначально было "раунд заканчивается, как только опустеет одна сторона" — это баг, поймано на реальном плейтесте.)*

## 4. Разрешение одного обмена

Пусть ведущий активировал `L` бит типа `T_L`, отвечающий — `R` бит типа `T_R` (`R` может быть 0, если не ответил).

- **attack vs defense** (в любом порядке — атаку блокирует защита независимо от того, кто из двоих вёл этот конкретный обмен, ведущий определяет только очерёдность **хода**, а не то, "чья атака приоритетнее"):
  - Каждая защита гасит одну атаку 1:1.
  - Если атак больше, чем защит — разница проходит уроном (по 1 урону за не заблокированную атаку).
  - Если защит больше или равно — урона нет (лишние защиты просто не используются, не переносятся на другие обмены).
- **attack vs attack** (оба выбрали "attack" — отвечающий не стал блокировать, а тоже атаковал): урон проходит **в обе стороны одновременно**, по числу активированных атак каждой стороны (никто никого не блокирует).
- **attack vs (нет ответа)**: вся активированная атака проходит полным уроном (см. предыдущий вопрос — договорились, что отсутствие ответа = отсутствие защиты).
- **defense vs что угодно, когда никто не атаковал** (ведущий сам решил "походить" защитой без непосредственной угрозы — редкий, но не запрещённый случай): эффекта нет, защита просто активирована и выбывает из пула на этот раунд без последствий (защита не накапливается на будущее — не имеет смысла играть "в пустоту", но правилами не запрещено).
- **action vs что угодно**: активированная "action"-бита не участвует в подсчёте урона напрямую — она увеличивает счётчик очков действия соответствующей стороны на 1 (то же значение, что раньше считалось по всем `action`-граням брошенных бит сразу). Способности (см. §5) списывают эти очки, когда игрок явно выбирает способность — активация action-биты сама по себе ничего не активирует, только "копит" ресурс.

Урон применяется к HP сразу по итогам обмена (не откладывается до конца раунда) — так же, как и раньше, `character.hp -= damageToPlayer` и т.д., просто теперь это происходит несколько раз за раунд (по разу на обмен), а не один раз в конце.

## 5. Способности (переворот/неблокируемый урон/переброс/зеркало) — не меняются концептуально

Существующие 4 способности (`docs/BATTLE_RULES.md` §3.1) остаются как есть — они списывают накопленные очки действия (§4, action-активации) на весь **раунд целиком**, не на конкретный обмен. Это значит:

- Игрок объявляет выбор способности **один раз за раунд** (как сейчас), но действовать она может, только когда у него накопилось нужное количество очков действия из уже проведённых обменов этого раунда — то есть выбор способности логично делать **после** того, как все свои `action`-биты уже активированы (иначе нечем платить).
- `AbilityResolver` не меняется по сути, меняется только момент вызова: раньше он получал сразу все брошенные грани и считал `action`-очки по ним; теперь `action`-очки нужно считать по **уже активированным** action-битам за раунд (переменная, растущая по ходу обменов), а не по всему броску сразу.
- Способность `flip` (переворот) нацелена на биты соперника — раньше это были "уже брошенные, но ещё не посчитанные" биты; теперь логичнее всего нацеливать её на **ещё не активированные** биты соперника (те, что ещё не сыграли в этом раунде) — переворачивать уже сыгранную (активированную и учтённую в уроне) биту бессмысленно, обмен уже разрешён.
- **Открытый вопрос** (рекомендация, не блокер): разрешить активировать способность как **отдельный тип хода** в обмене (наравне с attack/defense/action) — то есть в момент, когда у игрока есть накопленные action-очки, он может в свой ход вместо активации бит объявить "использую способность X" вне очереди обычных бит. Это самый гибкий вариант и не требует отдельного протокола поверх обменов. **Принято** — реализовано именно так: активация `action`-бит немедленно применяет способность (если хватает "стоимости" — `AbilityType::fixedCost()`), лишние очки в том же ходе используются как обычный переворот; после первого срабатывания способности за раунд дальнейшие `action`-ходы той же стороны тоже становятся обычным переворотом.
- **Зеркало урона** реализовано так, что оно отражает урон, полученный **в том же обмене**, где было активировано (а не только в последующих) — это самый естественный и просто реализуемый вариант; отдельно не уточнялось.

## 6. PvE/бот и авто-бой

`BotActionStrategy` (сейчас — эвристика выбора целей для flip) расширяется до **эвристики ведения обмена**: когда ход бота (как ведущего или отвечающего), бот должен решить:
- Что активировать первым (эвристика: атаковать, если есть чем, иначе защищаться, если под угрозой, иначе копить action).
- Как отвечать на ход игрока (эвристика: если игрок атакует и у бота есть defense — блокировать; если нет — атаковать в ответ, если есть чем).

Для текстового авто-боя (`/pve`, `/event-fight`, симуляция турнирного матча) — цикл обменов прогоняется полностью на сервере за один HTTP-вызов, как и раньше весь раунд целиком; итоговый лог обменов можно свернуть в те же поля `BattleRound` (или расширить `BattleRound`, чтобы хранить список обменов раунда для истории/отладки — см. §8).

## 7. PvP и синхронизация — самое большое изменение API

Раньше один раунд разрешался за один обмен `throw` → (`submit-actions` с обеих сторон) → `resolve`. Теперь внутри одного раунда — **несколько последовательных обменов**, каждый из которых требует хода то одной, то другой стороны, и отвечающий должен **видеть**, что выбрал ведущий, прежде чем отвечать (это не "оба выбирают одновременно вслепую", как сейчас с `actionTargets`, а строго по очереди).

Это значит:
- `POST /battles/{id}/throw` — без изменений (бросок + приоритет считается сразу и возвращается клиенту: кто ведёт первым).
- Новый шаг вместо `submit-actions`: `POST /battles/{id}/exchanges` — вызывается **ведущим**, тело `{ face: "attack"|"defense"|"action", bitIndices: number[] }`. Сервер проверяет, что это действительно очередь этого игрока, сохраняет выбор как "ожидает ответа" (аналогично текущему `pendingCharacterActionTargets`, но на уровне одного обмена, не раунда).
- `POST /battles/{id}/exchanges/{exchangeId}/respond` — вызывается **отвечающим**, тело `{ face, bitIndices }` или пусто (пас). Как только ответ получен — сервер разрешает обмен (§4), применяет урон, возвращает результат обеим сторонам, и передаёт очередь ведущего другой стороне.
- Опрос (polling) сохраняется как принцип синхронизации (см. `docs/BATTLE_ROOM_DESIGN.md`), но теперь клиенту нужно куда чаще спрашивать "чей сейчас ход и что там произошло" — вероятно, стоит объединить это в один `GET /battles/{id}` с полем вроде `pendingExchange: { leaderIsOpponent, face, bitIndices } | null`.
- Тайм-аут хода (§6 `BATTLE_ROOM_DESIGN.md`) нужно продумать заново — раньше был один дедлайн на весь раунд ("оба прислали actionTargets"), теперь дедлайн логичнее вешать на каждый обмен отдельно (и на ведущего, и на отвечающего).

Это самая трудоёмкая часть — фактически переписывается весь протокол раунда для PvP. Рекомендую сначала полностью реализовать и обкатать механику на PvE (где нет сетевой синхронизации, весь цикл обменов прогоняется на сервере одним вызовом), и только потом переносить на PvP-протокол — так же, как в этом проекте сначала строился PvE, а PvP добавлялся отдельным сприntom поверх готовой боевой математики.

## 8. Activity UI

`ArenaScreen` меняется существенно:
- После броска показывается не "выбери способность и подтверди", а: чей сейчас ход (приоритет), и если ваш — выбор группы бит одного типа для активации; если не ваш — ожидание/индикатор "соперник выбирает" с последующим показом того, что он выбрал, и вашим выбором ответа.
- Нужна визуализация "стопки" уже активированных бит за раунд (чтобы игрок видел прогресс обмена) отдельно от ещё не брошенных/не активированных бит.
- Лог обменов раунда стоит показывать построчно (как список сообщений "вы: 2 атаки → соперник: 1 защита → −1 HP сопернику"), а не одной строкой суммарного урона, как сейчас.

## 9. Что НЕ меняется

- Сам бросок бит (этап 1, случайность 50/50 на грань) — без изменений.
- 4 боевые способности по сути — без изменений, меняется только момент подсчёта action-очков (§5).
- Общая структура сущностей `Battle`/`BattleRound`/`Bit` — расширяется, не переписывается с нуля.
- HP/энергия/награды/турниры/ивенты — не затрагиваются этим документом.

2. Всё остальное в документе уже основано на ваших ответах в чате (преимущество — доп. свойство граней; частичный блок 1:1; отсутствие ответа = полный урон; ничья по преимуществу — случайно).

Если план в целом верный — начинаю с §1–§6 (данные + PvE), PvP-протокол (§7) и Activity UI (§8) — отдельными шагами после того, как боевая математика обкатана на PvE.
